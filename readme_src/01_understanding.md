# Part A: Understanding the Project

## 1. Executive Summary

The project builds a **physical, accessible kiosk**. A visitor can use it to explore Dr. B. R. Ambedkar's writings, constitutional-era records and media, and to **check each item against its source**.

The work is split between two tiers:

* **Raspberry Pi 5 (edge).**
  * Runs the display.
  * Reads a **PIR motion sensor** and a **physical HOME button** through GPIO.
  * Plays audio.
  * Keeps a **restricted, clearly labelled offline exhibit cache**.
* **Cloud backend (institution-scale services).**
  * Stores the catalogue, reviewed transcriptions, searchable passages and approved media.
  * Runs OCR processing, hybrid retrieval and a **source-grounded research-assistant workflow**.
  * The Pi **never** runs a large language model and **never** stores the master archive.

### 1.1 The demonstrable journey

```text
approach kiosk ─► motion wakes welcome screen ─► select a collection ─► search a verified source
      ─► inspect its original scan or media timestamp ─► ask a question ─► receive a cited answer
      ─► press HOME to clear the session
```

If the cloud cannot be reached, a clearly labelled **offline subset** stays available. The assistant **does not pretend** it can answer live questions.

### 1.3 Minimum success criteria (from the design document)

The six-week demonstration succeeds if it shows **all** of the following:

1. One source-linked item in **each of the five collection categories**.
2. A **sensor-driven welcome**: PIR → ATTRACT → HOME.
3. A **physical HOME/reset** that clears the visitor session.
4. **Scan-to-text navigation**: a result opens the correct scanned page next to reviewed text.
5. **Working search** over verified sources.
6. **Source-grounded answers**. Each factual answer links to a visible source span; otherwise the assistant **abstains**.
7. A **captioned media item** with transcript seek.
8. **Predictable offline behaviour.**

### 1.4 Explicitly out of scope for the six-week demo

* Owning an archive.
* Authoritative transcription of all manuscripts.
* High-volume video preservation.
* Live voice cloning. **Never** fabricate an "original" Ambedkar voice.
* Access to restricted archives without permission.
* Production-grade legal certification.
* Institution-wide procurement.

The prototype **can** become the foundation of a future installation. A real institution would additionally need all of these:

* digitisation agreements
* rights assessment
* accessibility auditing
* archival policy
* security review
* uptime operations
* staff training

See [§ 66](#66-prototype-versus-future-capability) and [§ 67](#67-scale-up-roadmap).

## 2. Honest Status and Claims Policy

This project deals with a person of great historical, constitutional and social significance, and with material held by other institutions. The engineering therefore follows a strict claims policy. **Every contributor accepts it.**

| # | Rule | What it means in practice |
|---|---|---|
| C-1 | **No ownership claims** | Nothing in the README, UI or marketing says the project owns, hosts or has rights to "the Ambedkar archive". Listing a source is not permission to mirror it. |
| C-2 | **No invented history** | The assistant, timeline and stories never produce a quotation, speaker, edition, page, date or translation that isn't in reviewed catalogue data. |
| C-3 | **Engineers do not self-certify history** | Historical accuracy is reviewed by a curator, historian, librarian or faculty member. A developer cannot tick the "reviewed" box on their own authority. |
| C-4 | **No certification claims** | No WCAG, GIGW, electrical-safety, EMC, privacy-law or security certification is claimed. WCAG 2.2 AA is an *evaluation target*. GIGW 3.0 is *assessed* for a government-facing deployment. |
| C-5 | **Targets are not results** | Planning charts carry a **TARGETS / ASSUMPTIONS** stamp. Measured results go in a separate test report with the date, hardware revision and corpus version. |
| C-6 | **Demo data is labelled** | Figures computed from the 14-item sample carry a **DEMO CORPUS** stamp. The sample is not a representative archive. |
| C-7 | **AI output is labelled** | Every generated text carries **AI SUMMARY** or **AI TRANSLATION**. The original scan or transcript is always one tap away. |
| C-8 | **Authentic ≠ synthetic** | Authentic recordings and modern or synthetic narration are separate media kinds with separate badges. They are never mixed. |
| C-9 | **Offline honesty** | When offline, the kiosk says so, disables live AI and explains why. It never shows a frozen spinner or a fake answer. |
| C-10 | **No secrets in Git** | Model keys, database credentials and signing keys live in a secret manager or CI secret store. The Pi holds only a narrowly scoped, revocable device credential. |
| C-11 | **Unknown stays unknown** | Values that have not been decided or measured are written `TBD` or `CONFIGURABLE`, never guessed. |

## 3. Problem Statement

Dr. Ambedkar-related works and historical records are **spread across institutions and media formats**:

* published collected works and translations
* Constituent Assembly debates in official reports
* periodicals
* manuscripts
* photographs
* audio and video recordings, including modern oral histories

The Dr. Ambedkar Foundation lists collected works and translations. The Parliament Digital Library lists the Constituent Assembly's draft-making debates. These are **candidate sources for an inventory, not automatic permission to mirror all content.**

A physical visitor interface is useful only if the underlying items meet four conditions:

1. **Discoverable.** A visitor can find them by title, name, date, topic or concept, in more than one language.
2. **Responsibly licensed.** Each use has a recorded rights decision: display, download, translation/derivative and AI processing.
3. **Historically attributable.** The system never confuses "authored by", "spoken by", "discusses", "edited by" and "portrays".
4. **Inspectable in original form.** Any text, summary or answer leads back to the original scan page or media timestamp.

### 3.1 Why a kiosk, and why embedded?

| Need | Why a web page alone is not enough | What the kiosk adds |
|---|---|---|
| Walk-in visitors at an exhibition, library or campus event | Visitors don't log in, install apps or type URLs | A self-starting exhibit that **wakes on approach** (PIR) and can **always be reset** by a large physical button |
| Shared public device | Browsers keep history, forms and media state | A session model that **wipes visitor state** on HOME or on timeout, with a warning first |
| Unreliable venue network | A cloud-only page shows a blank screen | A **signed offline bundle** of approved items, with honest offline labelling |
| Accessibility in a physical space | Screen height, angle, glare, noise | Seated reach, headphones, captions on by default, contrast and text-size controls, keyboard operation |
| Trust in AI answers | Generic chatbots invent quotes | A **server-side answer contract** that verifies every cited passage and abstains otherwise |

### 3.2 Why not run everything on the Pi?

Running full OCR, indexing and LLM inference for all collections on a Pi is impractical, and pretending otherwise would be dishonest. The Pi does what an embedded device does well: **sensing, local state, display, a small cache and failure handling.** The cloud does what needs institutional scale: **catalogue, preservation, OCR/ASR jobs, retrieval and model calls.**

## 7. System Architecture

### 7.1 Layers

| Layer | Runs on | Responsibilities | Must never |
|---|---|---|---|
| **L0 Physical** | Pi 5, touchscreen, PIR, HOME button, speaker/headphones, optional mic, NFC, LED | Sense presence, accept touch and button input, display and play media | Expose GPIO pins, power or mains to visitors |
| **L1 Embedded agent** | Pi (Python, systemd) | GPIO events, idle policy, health probe, manifest sync, loopback event relay | Send raw motion or button data to the cloud; hold admin credentials |
| **L2 Kiosk UI** | Pi (Chromium kiosk, static bundle served locally) | Navigation, viewer, media, citations, language, offline badges, session reset | Contain API secrets; load a cloud-only homepage |
| **L3 Local cache** | Pi (SQLite FTS5 + assets) | Approved public subset for offline browsing and keyword search | Contain masters, unapproved items, or anything past manifest expiry + grace |
| **L4 API gateway** | Cloud | TLS, rate limits, device identity | Trust the device for authorisation decisions |
| **L5 Archive services** | Cloud (FastAPI) | Catalogue, rights, items, pages, timeline, search, ask, offline manifest, admin | Return an item without a rights check |
| **L6 Data** | Cloud (PostgreSQL + pgvector, object storage) | Catalogue, passages, embeddings, audit, masters and derivatives | Overwrite masters; serve masters to the kiosk |
| **L7 Workers** | Cloud | OCR, ASR, fixity, embeddings, thumbnails | Publish anything; that is a human decision |
| **L8 Model providers** | External or self-hosted (TBD) | Generate concise answers from supplied evidence only | Receive ineligible passages or the whole vault |

### 7.2 Data flow in one visitor question

<div align="center">
<img src="diagrams/17_rag_sequence.png" alt="RAG sequence" width="900"/>
</div>

1. The visitor types a question on the kiosk. The UI sends `POST /v1/ask {query, language, device_id}` over HTTPS with the device credential.
2. The gateway checks device identity and the rate limit.
3. The API applies item-level and passage-level permissions **before** retrieval. It then runs lexical and dense search over **eligible** passages only.
4. Unreviewed OCR is dropped from exact quotation.
5. The model receives the excerpts and a guard instruction. It returns a short answer plus **supporting passage IDs**.
6. The verifier checks that every returned ID is in the retrieved set and still visible to the public role.
7. Citations are **assembled from catalogue metadata**: title, edition, printed page, PDF index, timestamp. Nothing comes from model text.
8. The response is `answered` (with citations), `not_verified` (no citations, honest message) or `unavailable` (offline).
9. The UI labels the text **AI SUMMARY** and renders citation chips that open the exact page or timestamp.

### 7.3 Architecture principles

| # | Principle | Consequence |
|---|---|---|
| P-1 | **The kiosk is untrusted** | Authorisation, rights and publication are decided in the cloud. The kiosk holds only public material and a revocable credential. |
| P-2 | **Rights before retrieval** | Ineligible text never reaches an index, a ranking, a log of candidates or a model context |
| P-3 | **Evidence, not eloquence** | Citations come from the catalogue. The model identifies IDs; the server verifies them. |
| P-4 | **Masters are sacred** | Originals keep their checksums and are never edited in place. Everything else is a derivative. |
| P-5 | **Fail usable, fail honest** | Network loss gives a labelled offline exhibit. Missing evidence gives "not verified". An expired manifest gives no cache. |
| P-6 | **One rule, one place** | Trust rules live in `reference/heritage_core` and are reused as test vectors by the services |
| P-7 | **Humans publish** | Workers propose and people approve. Sensitive publication needs two people. |
| P-8 | **Local first on the Pi** | Chromium loads the Pi-hosted UI, so a cloud outage never produces a blank kiosk |

## 8. Design Decision Record

Decisions are recorded as lightweight ADRs. The first seven come from the design document's decision record; the rest are added by this README.

| ADR | Decision | Prototype choice | Reason / boundary | Revisit when |
|---|---|---|---|---|
| ADR-01 | Embedded controller | **Raspberry Pi 5, preferably 8 GB RAM** | Pi OS can run the browser, GPIO, video and a small local cache. 4 GB may work with smaller page assets. | Thermal or memory tests fail (HW-04) |
| ADR-02 | AI location | **Cloud backend** | More practical than pretending the Pi performs full OCR, indexing and LLM inference for all collections | A small on-device model becomes demonstrably adequate *and* rights allow local processing |
| ADR-03 | Screen | **10–15-inch HDMI + USB capacitive touch** | Widely available. Exact power and mounting depend on the selected model. | Venue dictates size |
| ADR-04 | Hardware input | **PIR sensor + accessible physical HOME button** | A genuine embedded event chain in addition to touch | NFC tokens added (optional) |
| ADR-05 | Archive size | **Small samples from each of five categories** | Validates a common model and interface without assuming mass-digitisation rights | Institution pilot (Phase 2) |
| ADR-06 | Retrieval | **Keyword + vector search over reviewed excerpts** | Names, page numbers and quotations need exact matching; ideas benefit from semantic matching | Benchmarks show a dedicated engine is needed |
| ADR-07 | AI answers | **Only retrieved and permitted evidence, clickable citations** | Reduces false quotations and unverifiable claims | Never relaxed |
| ADR-08 | Network fallback | **Curator-selected local public subset; no live AI** | The failure mode is usable and honest | — |
| ADR-09 | Browser ↔ GPIO | **Loopback-only event service (POST → SSE)** | The browser can't read GPIO; loopback keeps hardware events off the network | Unix domain socket preferred for hardening |
| ADR-10 | Pin library | **GPIO Zero with the lgpio pin factory** | GPIO Zero documentation identifies lgpio as the supported factory for Pi 5 | Pi OS release changes the default |
| ADR-11 | Offline search | **SQLite FTS5** | Enough for small offline keyword search, zero server | Offline corpus grows past what FTS5 handles comfortably (measure) |
| ADR-12 | Knowledge map storage | **Reviewed relation table, no graph database** | A visual graph is an interface to reviewed relations, not a fact generator | Actual retrieval or curation requirements justify a graph DB |
| ADR-13 | Manifest signing | **HMAC-SHA256 in the reference; Ed25519 recommended for production** | HMAC is simple to test. An asymmetric signature means the Pi holds only a public key. | Before the Phase 2 pilot |
| ADR-14 | Evidence-sufficiency heuristic | **Query-term coverage ≥ 0.5 of content terms** (reference) | Cheap, deterministic abstention for out-of-scope questions in tests | Replace or augment with a curator-labelled benchmark and a model-side judgement, while **keeping** server-side ID verification |
| ADR-15 | Two-person publication | **Reviewer 1 (content) + Reviewer 2 (rights checkbox + publish)** | Mirrors the prototype curator console | Institution policy may require more |
| ADR-16 | IIIF | **Deferred** | Implementing the whole IIIF stack is not a prerequisite for a class demo | Interoperable page delivery is needed (Phase 3) |
